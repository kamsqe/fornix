# Blocks Agent

Last verified: 2026-03-03

## Purpose

Blocks are the atomic units of Fornix. Each block is a self-contained piece of functionality (UI section, integration, feature, or layout) that can be composed into an Astro project.

## Block Types

| Type | What It Is | Example |
|------|-----------|---------|
| `section` | Visual UI component | `hero-gradient`, `pricing-table`, `footer-minimal` |
| `integration` | Service/platform wiring | `db-d1`, `auth-better-auth`, `payments-stripe`, `analytics-cf` |
| `feature` | Full feature with pages + content | `blog-mdx`, `docs-collection` |
| `layout` | Page shell | `layout-marketing`, `layout-dashboard` |

## Block File Structure

Every block is a self-contained directory:

```
{block-name}/
├── block.json              # BlockManifest — identity, deps, AI metadata
├── {block-name}.astro      # Main Astro component
├── {block-name}.css         # Scoped styles (optional)
├── schema.ts               # Content collection schema (optional)
├── default-content.json    # Default content for the content slots
└── README.md               # Usage docs (optional)
```

## BlockManifest (`block.json`)

```typescript
BlockManifest {
  schemaVersion: number          // e.g. 1 — bumped when BlockManifest shape changes
  name: string               // kebab-case, e.g. "hero-gradient"
  version: string            // semver, e.g. "1.0.0"
  type: 'section' | 'integration' | 'feature' | 'layout'
  description: string        // max 200 chars
  category: string           // e.g. "hero", "pricing", "auth"
  tags: string[]

  dependencies: Record<string, string>   // npm packages this block needs
  requires: string[]                      // other blocks that must also be installed
  conflicts: string[]                     // blocks that cannot coexist

  requiredMode?: 'static' | 'hybrid' | 'server'  // minimum rendering mode
  envVars: Array<{ name, description, required }>  // env vars needed at runtime
  variants: string[]         // e.g. ['default', 'centered', 'split']
  slots: string[]            // named slots for composition

  files: Array<{
    source: string           // relative to block dir
    destination: string      // relative to project root
    condition?: string       // e.g. "renderMode !== 'static'"
  }>

  ai?: {
    whenToUse: string        // natural language guidance for AI
    whenNotToUse: string
    pairsWith: string[]      // blocks that work well together
    contentSlots: Record<string, {
      type: 'string' | 'number' | 'boolean' | 'array' | 'object'
      description?: string
      maxLength?: number
      example?: unknown
      items?: Record<string, unknown>
      minItems?: number
      maxItems?: number
    }>
  }
}
```

## Content Architecture

Content is **data, not code.** All text, images, and structured data live in `src/content/` as JSON or Markdown — completely separate from `.astro` components.

This means:
- Users edit content without touching components
- AI agents manage content via simple file edits (no AST parsing)
- Content is validated by Zod schemas
- Content can be sourced from anywhere (local → CMS → API)

### i18n Content Rules

When the project has `locales.length >= 2`:
- **Zero hardcoded text in any `.astro` file.** Every visible string must come from a content collection, keyed by locale.
- Content is organized per-locale: `src/content/{locale}/sections/hero.json`
- Components use a `t()` helper or read from the current locale's content collection
- Default content is generated by AI for ALL configured locales
- Even "single-locale" projects should keep text in content collections (blocks are designed this way), but the locale directory nesting is only added when 2+ locales are configured

## Schema Versioning & Migration

Every `block.json` has a `schemaVersion` field (integer). When the `BlockManifest` schema changes:

1. **Bump `schemaVersion`** in the schema definition
2. **Write a migration script** in `packages/fornix-registry/scripts/migrate-blocks.ts` that reads all blocks, transforms old fields to new ones, and writes updated `block.json` files
3. **The registry builder rejects blocks with outdated `schemaVersion`** — forces all blocks to be migrated before publishing
4. **`fornix doctor`** warns projects using blocks with an outdated manifest version

This ensures you can safely change the manifest shape even with 100+ blocks — run the migration script, and every block is updated.

## Block Combination Testing Strategy

At scale (50+ blocks), testing every combination is impossible. Use a tiered approach:

| Tier | What | Scope |
|------|------|-------|
| **Isolation** | Every block scaffolds alone | All blocks (automated) |
| **Recipes** | Each recipe's exact block set | 5-6 recipes (automated) |
| **Pairwise** | Each block pair that declares `pairsWith` | ~20-30 pairs (automated) |
| **Conflict** | Every `conflicts` pair is tested for rejection | All declared conflicts (automated) |
| **Random** | CI picks 5 random 3-block combinations per run | Rotating coverage (automated, CI-only) |

Do NOT try to test the full N×N matrix. The isolation + recipe + pairwise tiers catch 95%+ of real issues.

## Anti-Patterns

- **Never** import from one block into another block's files
- **Never** hardcode content text in `.astro` files — use content collections
- **Never** create a block without a `block.json` manifest
- **Never** add npm dependencies outside of the manifest's `dependencies` field
- **Never** put user-visible strings directly in component markup — every string must route through content collections, even for single-locale projects (this keeps blocks i18n-ready by default)
